# 모델 호출 단계 전반부 설계

## 의도

학습자는 Spring AI로 모델을 불러 본 적이 있지만, 그때 LLM API가 정확히 어떻게 호출되고 응답이 어떤 모양으로 오는지는 알지 못했다. 라이브러리가 요청을 만들고 응답을 풀어 주면서 실제로 오가는 내용을 감췄기 때문이다.

이번 주의 목적은 그 감춰진 부분을 직접 다뤄 보는 것이다. 성공 기준은 학습자가 Spring AI 호출 한 줄을 보고 그 아래에서 나가는 HTTP 요청과 돌아오는 응답을 머릿속으로 그릴 수 있는 상태다. 예를 들어 `chatClient.prompt().system(...).user(...).call().content()`를 보면 다음을 설명할 수 있어야 한다.

- `system`과 `user`가 요청 본문의 `messages` 배열에서 어떤 원소가 되는지 설명할 수 있다.
- 모델 이름과 온도 같은 옵션이 요청 본문의 어디에 들어가는지 설명할 수 있다.
- `content()`가 응답 JSON의 어느 경로에서 값을 꺼내는지 설명할 수 있다.
- `content()`가 버리는 정보를 설명할 수 있다. `usage`의 토큰 수, `finish_reason`, `id`, `model`이 그 예다.
- 여러 턴 대화에서 이전 대화 전체가 요청마다 다시 보내진다는 사실을 직접 확인했다.
- 키가 틀렸을 때와 429 응답이 왔을 때 상태 코드와 본문이 어떤 모양인지 직접 확인했다.

이 문서는 `docs/roadmap.md`의 "모델 호출" 단계 2주 가운데 앞의 1주를 다룬다.

## 목표

- Chat Completions API를 Ktor 클라이언트로 직접 호출하는 최소한의 클라이언트를 `framework` 모듈에 만든다.
- 예제 모듈에 모델을 부르는 응답기를 추가하고, 터미널 채팅에서 실제 모델과 대화한다.
- 채팅 중에 실제로 오간 요청과 응답 JSON 원문을 화면에 보여 줄 수 있다.
- 호출마다 입력 토큰, 출력 토큰, 추정 비용을 화면에 보여 준다.
- 정해진 실험을 예측과 실행 순서로 진행하고, 학습자가 직접 쓴 학습 기록을 남긴다.

## 비목표

다음 항목은 모델 호출 단계 후반부로 미룬다. 후반부는 이번 주에 겪은 문제를 바탕으로 따로 설계한다.

- 지수 백오프 재시도와 시간 제한 정책.
- 응답 기록과 재생.
- 월 비용 상한 장치.
- 모델 호출 인터페이스를 일반화해서 로컬 모델 서버로 바꿔 끼우는 일.
- Responses API와의 비교 실험.
- 호출 실패율 측정을 위한 응답 지연 프록시.

다음 항목은 로드맵의 다른 단계에서 다룬다.

- 툴 호출은 툴 호출 루프 단계에서 다룬다.
- 스트리밍 응답은 스트리밍 단계에서 다룬다.

## 반목표

다음 상황은 코드가 동작하더라도 이번 주의 실패로 본다.

- 코드는 돌아가는데 학습자가 왜 그렇게 동작하는지 설명하지 못한다.
- 학습자가 설계하기로 한 핵심 코드를 Claude가 지시 없이 스스로 설계해 버린다.
- 실험 결과를 예측 없이 실행만 하고 넘어간다.

## 제약

- `docs/roadmap.md`의 제약을 그대로 따른다. 그중 이번 주에 직접 걸리는 제약은 다음과 같다.
- 공식 OpenAI SDK, Spring AI, LangChain4j를 쓰지 않는다. HTTP는 Ktor 클라이언트, 직렬화는 kotlinx.serialization을 쓴다.
- API 키는 `OPENAI_API_KEY` 환경 변수에서만 읽는다. 키는 저장소, 로그, 화면 출력 어디에도 남기지 않는다. 요청 원문을 보여 줄 때 `Authorization` 헤더 값은 가린다.
- OpenAI 비용은 한 달에 5,000원 이하로 유지한다. 이번 주 실험은 가장 저렴한 소형 모델로 수십 번 안팎의 호출만 한다.
- `framework` 모듈에는 주문, 환불, 배송 같은 쇼핑몰 개념이 들어가지 않는다.
- 채팅 화면의 문구, 시스템 프롬프트, 커밋 메시지는 한국어로 쓴다.

## 정해진 방식

### 역할 분담

호출의 핵심 코드는 학습자가 설계하고, 타이핑은 Claude가 한다. 학습자가 무엇을 어떻게 쓸지 구체적으로 지시하면 Claude는 지시한 내용만 그대로 코드로 옮긴다. 지시에 없는 필드, 분기, 예외 처리를 Claude가 덧붙이지 않는다. 지시가 모호하거나 지시대로 쓰면 컴파일되지 않거나 동작이 틀리면, Claude는 고치지 않고 그 사실을 알린 뒤 학습자의 다음 지시를 기다린다. 핵심 코드는 다음 네 가지다.

- Chat Completions 요청 본문과 응답 본문을 나타내는 Kotlin 데이터 클래스.
- 헤더를 붙여 요청을 보내는 코드.
- 응답을 풀어 읽고 필요한 값을 꺼내는 코드.
- 성공 응답과 실패 응답을 구분하는 코드.

핵심 코드의 모양도 학습자가 정한다. 데이터 클래스의 필드 이름, 클라이언트 함수의 시그니처와 반환 타입, 실패를 예외로 던질지 결과 타입으로 돌려줄지가 여기에 들어간다. Claude는 이 모양을 미리 정해 두지 않는다.

Claude는 그 주변을 스스로 판단해서 작성한다. Gradle 의존성을 추가하고, 핵심 코드가 들어갈 파일 자리를 만들고, 채팅 명령과 응답기 연결을 맡는다. 테스트는 학습자가 핵심 코드의 모양을 정한 뒤에 그 모양에 맞춰 Claude가 쓴다. 핵심 코드를 지시대로 옮긴 뒤에는 그 코드를 검토하고 각 필드와 동작을 설명한다. 학습자가 막혀서 요청하기 전에는 핵심 코드를 스스로 판단해서 채우지 않는다.

### JSON 변환

Ktor의 `ContentNegotiation` 플러그인과 kotlinx.serialization의 자동 변환을 쓴다. 학습자는 JSON 변환 자체는 이미 이해하고 있어서 이 부분은 감춰져도 된다고 판단했다.

다만 실제로 오간 JSON 원문은 볼 수 있어야 한다. 채팅 화면에 요청과 응답 원문을 그대로 출력하는 설정을 둔다.

### 예측하고 실행하기

실험마다 학습자가 결과를 먼저 예측해서 적고, 실행한 뒤 예측과 비교한다. 실험 목록은 다음과 같다.

- 시스템 메시지와 사용자 메시지 하나로 처음 호출하고, 응답 JSON의 최상위 필드를 하나씩 읽는다.
- `max_tokens`를 아주 작게 주고 `finish_reason`과 출력 토큰 수가 어떻게 바뀌는지 본다.
- 같은 질문을 온도 0과 높은 온도로 여러 번 보내고 응답이 얼마나 달라지는지 본다.
- 세 턴 이상 대화하면서 턴마다 입력 토큰이 어떻게 늘어나는지 본다.
- 잘못된 API 키로 호출해서 상태 코드와 오류 본문을 본다.
- 존재하지 않는 모델 이름으로 호출해서 상태 코드와 오류 본문을 본다.
- 429 응답을 실제로 겪어 본다. 짧은 시간에 요청을 몰아 보내도 429가 나지 않으면, 겪지 못했다는 사실과 시도한 방법을 기록하고 후반부의 지연 프록시로 넘긴다.
- 시스템 프롬프트에 주문 정보를 주지 않은 채 주문 상태를 물어보고, 모델이 답을 지어내는지 본다. 이 결과가 로드맵에 적힌 이 단계의 "드러날 한계"다.

실험에 쓰는 모델은 온도와 `max_tokens`를 받는 비추론 소형 모델 가운데 가장 저렴한 것으로 고른다. 가장 저렴한 모델이 추론 모델이라 온도를 거부하거나 `max_completion_tokens`만 받으면, 온도 실험과 `max_tokens` 실험의 의도대로 관찰할 수 없기 때문이다. 이 선택은 Claude의 판단이다.

실험에 필요한 조작은 채팅 안의 명령으로 제공한다. 모델 이름, 온도, `max_tokens`를 바꾸는 명령, 대화 기록을 비우는 명령, 원문 출력을 켜고 끄는 명령이 여기에 들어간다. 429 실험처럼 요청을 짧은 시간에 몰아 보내는 일은 채팅 루프와 맞지 않으므로 별도 명령줄 명령으로 둔다. 이 배치는 Claude의 판단이다.

### 학습 기록

학습 기록은 학습자가 자기 말로 쓴다. 기록에는 실험마다 예측, 실제 결과, 둘이 달랐던 이유를 적는다. Claude는 기록을 검토하고 틀린 설명이나 빠진 부분을 지적한다.

이번 주의 마지막 확인으로, 학습자가 Spring AI 호출 코드 한 토막을 보고 그 코드가 만드는 HTTP 요청과 응답을 아무것도 보지 않고 손으로 적는다. 적은 내용을 실제 원문과 비교해서 맞지 않는 부분이 없으면 이번 주를 마친다.

### 모듈 배치

모델 호출 클라이언트와 요청, 응답 데이터 클래스는 `framework` 모듈에 둔다. 이 코드는 다른 에이전트에도 쓸모가 있기 때문이다.

모델을 부르는 응답기는 예제 모듈에 둔다. 이 응답기는 기존 `aiagent.shop.scenario.Responder` 인터페이스를 구현하고, 쇼핑몰 상담원 역할의 시스템 프롬프트와 대화 기록을 가진다. 채팅 명령은 기존 정규식 응답기와 모델 응답기 가운데 하나를 고를 수 있어야 한다. `scenarios` 명령은 비용 때문에 이번 주에도 정규식 응답기만 쓴다.

호출이 실패하면 채팅은 멈추지 않고 상태 코드와 오류 메시지를 보여 준 뒤 다음 입력을 받는다. 실패한 턴의 사용자 메시지는 대화 기록에 남기지 않는다. 남기면 다음 요청에 응답 없는 사용자 메시지가 섞여서 입력 토큰 증가 실험의 결과가 흐려지기 때문이다. 이 두 가지는 Claude의 판단이다.

### 시험

자동 테스트는 네트워크 없이 돈다. Ktor의 `MockEngine`으로 다음을 확인한다.

- 보낸 요청의 경로, 헤더, 본문이 기대한 모양이다.
- 기록해 둔 실제 응답 JSON을 넣었을 때 내용, 토큰 수, `finish_reason`을 올바르게 꺼낸다.
- 오류 응답 JSON을 넣었을 때 성공으로 착각하지 않고 상태 코드와 오류 메시지를 드러낸다.

실제 API 호출은 자동 테스트에 넣지 않는다. 비용이 들고 결과가 매번 달라지기 때문이다. 실제 호출은 실험 시간에 채팅과 몰아 보내기 명령으로만 한다.

테스트에 넣는 응답 JSON은 처음에 OpenAI 공식 문서의 예시로 만든다. 첫 실험에서 실제 응답을 받으면 그 원문으로 바꾼다. 이 순서는 Claude의 판단이다.

## 구현자에게 맡기는 부분

- 파일과 클래스, 함수의 이름과 패키지 구성.
- 사용할 소형 모델의 구체적인 이름과 토큰당 가격. 위 실험 절의 조건에 맞춰 구현 시점의 OpenAI 가격표를 보고 정하고, 가격은 코드 한 곳에 상수로 둔다.
- 채팅 안 명령의 이름과 문법.
- 원문을 Ktor의 `Logging` 플러그인으로 볼지, 응답 본문을 문자열로 한 번 더 읽어 볼지의 결정.
- 학습 기록 파일의 위치와 형식.
- 실험에서 호출 원문과 응답을 테스트용 고정 데이터로 저장해 둘지의 결정.
