# 툴 호출 루프 단계 전반부 설계

## 의도

모델 호출 단계의 실험에서 모델은 주문 정보를 조회할 수단이 없었다. 그래서 "주문번호 ORD-0001 지금 어디쯤 왔어요?"라는 질문에 "배송 중, 내일 도착"이라고 지어냈다. 시드 42의 실제 상태는 "상품 준비 중, 출고 대기"다. 학습자는 이 장면을 실제 상담 서비스였다면 가장 곤란했을 순간으로 꼽았다.

이번 단계에서는 모델에게 주문 서비스와 배송 서비스를 조회하는 툴을 쥐여 주고, 답이 실제 데이터에서 나오게 만든다. 학습자가 이해하고 싶은 것은 다음 두 가지다.

- 모델이 툴을 불러 달라고 할 때 돌려주는 응답이 정확히 어떤 형식인지.
- 그 응답을 받은 뒤 실제 툴 함수가 어떤 과정을 거쳐 호출되고, 결과가 어떻게 모델에게 돌아가는지.

두 가지를 이어 주는 앞 단계로, 모델이 어떤 툴이 있는지를 어떻게 아는지도 함께 다룬다.

이 문서는 `docs/roadmap.md`의 "툴 호출 루프" 단계 2주 가운데 앞의 1주를 다룬다.

## 단계 순서 변경

로드맵의 순서로는 모델 호출 단계 후반부가 먼저다. 후반부는 재시도와 시간 제한, 응답 기록과 재생, 월 비용 상한, 로컬 모델 교체를 다룬다. 학습자는 툴 호출 루프를 먼저 하기로 정했다. 이유는 다음과 같다.

- 학습자가 꼽은 가장 큰 문제인 주문 상태 지어내기는 후반부 항목으로는 풀리지 않는다.
- 모델 호출 단계의 실험에서 후반부 항목은 실제 문제로 드러나지 않았다. 요청 100개를 몰아 보내도 429가 나지 않았고, 시간 초과도 없었으며, 일주일 비용은 약 0.7원이었다.

후반부 항목은 실제로 문제가 될 때 그 자리에서 다룬다. 예를 들어 시나리오를 반복해서 돌리다 비용이 쌓이면 응답 기록과 재생을 다룬다.

## 성공 기준

학습자가 정한 성공 장면은 주문번호를 주면 모델이 실제 주문 상태로 답하는 것이다. 구체적으로는 다음과 같다.

- 모델 응답기로 채팅을 열고 시드 42에서 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 보내면, 모델이 툴을 불러 얻은 실제 값으로 답한다. 주문 상태는 "상품 준비 중"이어야 하고, 배송 상태를 말한다면 "출고 대기"여야 한다. 지어낸 상태가 하나라도 섞이면 실패다.
- 모델이 두 툴을 모두 부르는지는 합격 조건이 아니라 관찰할 내용이다. 주문 조회 툴 하나만 부르고 끝내더라도 답이 실제 값과 맞으면 성공이다. 두 툴을 다 부르게 만들려고 시스템 프롬프트나 툴 설명을 미리 고치지 않는다. 이 판단은 Claude가 학습자의 성공 기준인 "실제 주문 상태로 답한다"에서 이끌어 냈다.
- 원문 출력을 켜면 학습자가 다음을 직접 확인할 수 있다. 요청에 실린 툴 정의, 툴 호출 응답의 형식, 툴 결과를 실은 다음 요청, 최종 답이 나오기까지 오간 요청의 수.

## 목표

- 학습자가 다음 네 부분을 설계하고, Claude가 지시대로 옮긴다.
  - 툴 정의를 요청에 싣는 부분.
  - 모델의 툴 호출 응답을 읽는 부분.
  - 호출할 툴을 골라 실행하는 부분.
  - 툴 결과를 돌려보내며 최종 답이 나올 때까지 반복하는 루프.
- 대화 기록을 예제 모듈의 `ModelResponder`에서 프레임워크로 옮긴다. 툴 호출 메시지 때문에 기록의 모양이 바뀌므로, 그 모양은 루프 설계의 일부로 학습자가 정한다.
- 예제 모듈에 주문 조회 툴과 배송 조회 툴을 만들고 가짜 서비스에 연결한다.
- 실험을 예측과 실행 순서로 진행하고, 학습자가 직접 쓴 학습 기록을 남긴다.

## 비목표

다음 항목은 이 단계의 후반부로 미룬다. 후반부는 전반부 실험에서 실제로 드러난 실패를 바탕으로 따로 설계한다.

- 존재하지 않는 주문번호, 모호한 요청, 장애 주입으로 일으킨 툴 오류에 대한 대응.
- 루프 종료 조건 외의 최대 반복 수 제한과 같은 호출의 반복 감지.
- 툴 오류를 모델이 읽을 수 있는 결과로 돌려주는 처리.
- 여러 툴 호출의 코루틴 병렬 실행.
- Kotlin 함수 정의에서 JSON 스키마를 자동으로 만드는 일.
- 시나리오 실행기로 성공률, 루프 반복 수, 실패 유형별 건수를 재는 일.

다음 항목은 로드맵의 다른 단계에서 다룬다.

- 스트리밍 응답은 스트리밍 단계에서 다룬다.
- 대화 기록을 자르거나 요약하는 일은 컨텍스트 관리 단계에서 다룬다.
- 환불이나 교환처럼 상태를 바꾸는 툴은 상태 모델링 단계 이후에 다룬다. 이번 단계의 툴은 조회만 한다.

## 반목표

다음 상황은 코드가 동작하더라도 이번 주의 실패로 본다.

- 코드는 돌아가는데 학습자가 왜 그렇게 동작하는지 설명하지 못한다.
- 학습자가 설계하기로 한 네 부분을 Claude가 지시 없이 스스로 설계해 버린다.
- 실험 결과를 예측 없이 실행만 하고 넘어간다.
- 겪어 보지 않은 실패에 대한 대응을 미리 넣는다.

## 제약

- `docs/roadmap.md`의 제약과 모델 호출 단계 설계의 제약을 그대로 따른다.
- 모델은 `gpt-4o-mini`를 쓴다. 기존 `ModelPricing.DEFAULT_MODEL`이다.
- `framework` 모듈에는 주문, 배송, 환불 같은 쇼핑몰 개념이 들어가지 않는다. 툴 정의와 실행의 틀은 프레임워크에, 주문 조회 툴과 배송 조회 툴은 예제 모듈에 둔다.
- 기존 핵심 코드인 `ChatRequest`, `ChatResponse`, `OpenAiClient`를 바꿔야 하면 그 변경도 학습자가 지시한다.
- 자동 테스트는 실제 API를 부르지 않는다.

## 정해진 방식

### 역할 분담

모델 호출 단계와 같은 방식을 쓴다.

- 학습자가 네 부분의 모양과 내용을 정해 구체적으로 지시한다. 클래스와 함수의 이름, 시그니처, 데이터 구조, 실패를 표현하는 방식이 여기에 들어간다.
- Claude는 지시한 내용만 옮긴다. 지시에 없는 필드, 분기, 예외 처리를 덧붙이지 않는다.
- 지시가 모호하거나, 지시대로 쓰면 컴파일되지 않거나, 동작이 틀리면 Claude는 고치지 않는다. 그 사실을 알리고 학습자의 다음 지시를 기다린다. 이때 Claude는 제안을 함께 적을 수 있다.
- Claude는 그 주변을 스스로 판단해서 작성한다. Gradle 설정, 주문 조회 툴과 배송 조회 툴, 채팅 연결, 테스트가 여기에 들어간다. 테스트는 학습자가 네 부분의 모양을 정한 뒤에 그 모양에 맞춰 쓴다.
- 코드를 옮기기 전에 Claude는 OpenAI 문서에서 필요한 형식을 확인해 학습자에게 보여 준다. 보여 주는 시점은 아래 진행 순서를 따른다.

### 툴 구성

이번 주의 툴은 다음 두 개다. 이 구성은 Claude의 판단이다.

- 주문 조회 툴은 주문번호를 받아 `OrderService.getOrder`를 부른다.
- 배송 조회 툴은 주문번호를 받아 `ShippingService.getShipment`를 부른다.

툴 정의의 JSON 스키마는 처음에는 손으로 쓴다. 자동 생성은 손으로 쓰는 것이 실제로 불편해졌을 때 다룬다. 이 순서는 Claude의 판단이다.

모델이 툴 호출을 한 번에 여러 개 돌려주면 이번 주에는 차례로 실행한다. 병렬 실행은 지연이 실제 문제가 될 때 다룬다. 이 순서도 Claude의 판단이다.

툴 결과를 모델에게 돌려줄 때 주문 상태와 배송 상태를 어떤 형식으로 담을지는 툴을 실행하는 부분의 일부로 학습자가 정한다.

### 진행 순서

학습자가 가장 알고 싶은 것은 툴 호출 응답의 형식이다. 응답을 읽는 코드를 먼저 설계하면, 응답 형식을 예측하는 실험이 정답을 적는 일이 되어 버린다. 그래서 코드와 실험을 다음 순서로 섞어서 진행한다. 이 순서는 Claude의 판단이다.

1. 학습자가 툴 정의를 요청에 싣는 부분을 설계한다. Claude는 그 전에 OpenAI 문서의 툴 정의 요청 형식만 보여 주고, 툴 호출 응답 형식은 보여 주지 않는다.
2. 아래 실험 목록의 첫 세 실험을 진행한다. 기존 응답 클래스는 모르는 키를 무시하고 원문 출력은 응답 전체를 보여 주므로, 응답을 읽는 코드 없이도 툴 호출 응답을 원문으로 볼 수 있다.
3. 세 번째 실험에서 받은 실제 툴 호출 응답을 보고, 학습자가 응답을 읽는 부분, 툴을 골라 실행하는 부분, 루프를 설계한다. 툴 호출 응답의 테스트용 고정 데이터는 처음부터 이 실제 응답으로 만든다.
4. 나머지 실험을 진행한다.

툴 정의를 싣지 않은 요청과 비교할 수 있도록, 채팅에는 툴 정의를 켜고 끄는 명령을 둔다. 한 턴 안에서 요청이 여러 번 나가면 요청마다 토큰 줄을 하나씩 보여 준다. 두 가지 모두 Claude의 판단이다.

### 예측하고 실행하기

모델 호출 단계와 같이 실험마다 학습자가 결과를 먼저 예측해서 적고, 실행한 뒤 예측과 비교한다. 실험 목록은 다음과 같다.

- 툴 정의를 실으면 같은 질문의 입력 토큰이 얼마나 늘어나는지 본다.
- 툴을 실은 채 "안녕하세요."처럼 툴이 필요 없는 말을 보내면, 모델이 툴을 부르는지 본다.
- 주문번호 ORD-0001의 배송 상태를 물으면 툴 호출 응답이 어떤 모양으로 오는지 본다. `finish_reason`, `content`, 툴 호출 정보의 위치와 인자 형식을 확인한다.
- 같은 질문에서 최종 답이 나오기까지 요청이 몇 번 오가는지, 툴을 하나씩 부르는지 한 번에 여러 개 부르는지 본다.
- 모델 호출 단계의 여덟 번째 실험을 같은 질문으로 다시 돌려 답이 실제 상태와 맞는지 본다.
- 주문번호 없이 "제 주문 어디쯤 왔어요?"를 보내면 모델이 툴을 부르는지, 주문번호를 묻는지, 인자를 지어내서 부르는지 본다. 이 결과는 후반부의 재료가 된다.

### 학습 기록

학습 기록은 `docs/learning/stage2-tool-loop.md`에 둔다. 모델 호출 단계와 같은 형식을 따른다. 실험마다 예측, 실제 결과, 달랐던 이유를 적고, 학습자가 자기 말로 쓰며 Claude는 지시한 내용을 옮긴 뒤 검토한다.

이번 주의 마지막 확인은 모델 호출 단계에서 바꾼 방식을 따른다. Spring AI의 툴 호출 코드 한 토막을 보고, 각 부분이 요청과 응답의 어디에 대응하는지 학습자가 말로 설명한다. 확인하는 내용은 툴 정의가 실리는 위치, 툴 호출 응답의 형식, 툴을 실행하는 주체, 결과가 돌아가는 형식, 루프가 끝나는 조건이다.

학습 기록 끝에는 "후반부로 넘길 문제"를 둔다. 이 목록이 후반부 설계의 출발점이다.

### 시험

자동 테스트는 `MockEngine`이나 가짜 `ChatClient`로만 돈다. 테스트로 확인할 내용은 학습자가 정한 모양에 맞춰 Claude가 정하되, 최소한 다음을 포함한다.

- 요청 본문에 툴 정의가 기대한 모양으로 실린다.
- 툴 호출 응답 JSON을 넣으면 툴 이름과 인자를 올바르게 꺼낸다.
- 툴 호출 응답 뒤에 툴 결과를 실은 다음 요청이 나가고, 툴 호출이 없는 응답이 오면 루프가 끝난다.
- 예제 모듈의 두 툴이 시드 42의 가짜 서비스에서 실제 값을 돌려준다.

툴 호출 응답의 테스트용 고정 데이터는 세 번째 실험에서 받은 실제 응답 원문으로 만든다.

## 구현자에게 맡기는 부분

- 주문 조회 툴과 배송 조회 툴의 이름, 설명 문구, 파일 위치.
- 시스템 프롬프트를 툴 사용에 맞게 고칠지의 결정. 고친다면 그 내용을 학습자에게 보여 주고, 실험 결과에 영향을 주는 변경이라는 점을 학습 기록에 남긴다.
- 채팅 화면에 툴 호출과 결과를 원문 출력과 별도로 짧게 보여 줄지의 결정.
- 학습 기록 파일의 세부 형식.
