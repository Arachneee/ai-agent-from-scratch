# 툴 호출 루프 단계 학습 기록

이 기록은 툴 호출 루프 단계 전반부의 실험을 남긴다. 실험마다 실행하기 전의 예측, 실제 결과, 둘이 달랐던 이유를 적는다.

## 툴 정의가 늘리는 입력 토큰

### 예측

`/tools off`일 때 입력 토큰은 모델 호출 단계의 첫 호출과 같은 54개다. `/tools on`일 때는 54개에 툴 정의를 구분하는 토큰과 툴마다 붙은 설명의 토큰이 더해진다.

### 실제 결과

온도 0에서 "안녕하세요."를 보냈다. `/tools off`일 때 입력 토큰은 54개였고, `/tools on`일 때는 137개였다. 툴 정의 두 개가 입력 토큰을 83개 늘렸다. 출력 토큰은 두 경우 모두 11개였다.

Claude가 `o200k_base`로 툴 정의를 두 가지 모양으로 세어 비교했다.

- 보낸 JSON을 그대로 세면 121개이고, 이 모양이라면 입력 토큰은 175개가 된다.
- 정의를 아래와 같은 함수 선언 형태의 글로 바꿔서 세면 84개이고, 이 모양이라면 입력 토큰은 138개가 된다.

```
# Tools

## functions

namespace functions {

// 주문번호로 주문 상태를 조회한다.
type get_order = (_: {
// 주문번호. 예: ORD-0001
order_id: string,
}) => any;

// 주문번호로 배송 상태를 조회한다.
type get_shipment = (_: {
// 주문번호. 예: ORD-0001
order_id: string,
}) => any;

} // namespace functions
```

실제 값 137개는 두 번째 모양과 1개 차이다. 그래서 서버는 JSON을 그대로 넣지 않고 이런 글로 바꿔서 넣는 것으로 보인다. 이 형식은 OpenAI 공식 문서에 없고, 토큰 수가 거의 맞는다는 점만이 근거인 추정이다. 이 모양으로 나누어 세면 머리말과 꼬리말이 13개, `get_order`가 36개, `get_shipment`가 37개다.

### 달랐던 이유

툴 구분 토큰과 툴마다 붙은 설명의 토큰이 더해진다는 구조는 맞았다. 그러나 툴 설명뿐 아니라 인자 이름과 타입, 인자 설명까지 들어간다는 것은 생각하지 못했다.

## 툴이 필요 없는 말

이 실험은 따로 돌리지 않고 첫 실험의 `/tools on` 요청으로 대신했다. 결과를 먼저 본 뒤라 예측은 남기지 않았다.

### 실제 결과

툴을 실은 채 "안녕하세요."를 보내자 모델은 툴을 부르지 않고 바로 답했다. 출력 토큰은 툴을 싣지 않았을 때와 같은 11개였고, 툴을 불렀다면 나왔을 `[빈 응답]`도 나오지 않았다. 답의 문장은 기록하지 않았다.

## 툴 호출 응답의 모양

### 예측

툴을 켜고 원문 출력을 켠 채 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 보낸다. `finish_reason`은 `tool_calls`이고 `content`는 null일 것이다. 툴 호출 정보가 응답 JSON의 어디에 들어 있는지와 `order_id` 인자가 어떤 형식으로 오는지는 예측하지 못했다.

### 실제 결과

처음 실행에서는 첫 실험 뒤 툴이 꺼진 채로 남아 있어 요청에 `tools` 키가 없었다. 모델은 모델 호출 단계의 여덟 번째 실험처럼 "배송 중이며, 예상 도착일은 내일"이라고 지어냈고, 입력 토큰은 67개였다. 툴을 켜고 다시 보낸 결과는 다음과 같다.

```json
"message": {
  "role": "assistant",
  "content": null,
  "tool_calls": [
    {
      "id": "call_wmZpVWpDAVRahYjHIoYmuxm5",
      "type": "function",
      "function": {
        "name": "get_shipment",
        "arguments": "{\"order_id\":\"ORD-0001\"}"
      }
    }
  ],
  "refusal": null,
  "annotations": []
},
"finish_reason": "tool_calls"
```

- `finish_reason`은 `tool_calls`였고 `content`는 null이었다.
- 툴 호출 정보는 `choices[0].message` 안의 `tool_calls` 배열에 들어 있었다. 원소마다 호출 `id`, `type`, 그리고 `function`의 `name`과 `arguments`가 있다.
- `arguments`는 JSON 객체가 아니라 JSON을 담은 문자열이었다. 따옴표가 `\"`로 이스케이프되어 있다.
- 모델은 `get_order`와 `get_shipment` 중 `get_shipment` 하나만 불렀다.
- 입력 토큰은 150개, 출력 토큰은 19개였다. 툴이 없을 때의 67개에 첫 실험에서 잰 툴 정의 83개를 더한 값과 같다.
- 채팅에는 `[빈 응답] finish_reason=tool_calls`가 보였다. 응답을 읽는 코드가 아직 `tool_calls`를 모르기 때문이다.

응답 본문은 `framework/src/test/resources/openai/chat-completion-tool-calls.json`에 저장했다.

### 달랐던 이유

`finish_reason`과 `content`는 예측대로였다. 인자가 JSON 객체가 아니라 JSON을 담은 문자열로 온다는 것은 예측하지 못했다.

## 최종 답까지 오가는 요청

### 예측

툴을 켜고 온도는 기본값으로 둔 채 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 보낸다. 요청은 두 번 오가고, 모델은 `get_shipment` 하나만 부를 것이다.

### 실제 결과

요청은 두 번 오갔다. 첫 응답에서 모델은 `get_shipment` 하나만 불렀고, 둘째 응답이 최종 답이었다.

- 첫 요청은 입력 150개, 출력 19개였다. 세 번째 실험의 툴 호출 응답과 같은 값이다.
- 둘째 요청은 입력 207개, 출력 51개였다. 첫 요청에 assistant의 툴 호출 메시지와 tool 결과 메시지가 더해져 입력이 57개 늘었다.
- 한 턴의 비용은 약 0.134원이었다.

### 달랐던 이유

예측대로였다.

## 주문 상태를 다시 묻기

### 예측

모델 호출 단계의 여덟 번째 실험과 같은 질문을 툴을 켠 채 보낸다. 이번 답은 시드 42의 실제 상태와 맞을 것이다. 이 실험은 앞 실험과 같은 실행으로 본다.

### 실제 결과

답은 "주문번호 ORD-0001의 배송 상태는 \"준비 중\"입니다. 예상 배송일은 2026년 1월 1일입니다."였다. 상태와 날짜는 툴 결과 `{"orderId":"ORD-0001","status":"READY","eta":"2026-01-01T00:00:00Z"}`에서 왔고, 모델 호출 단계처럼 지어낸 값은 없었다. 이번 주의 성공 기준을 통과한 것으로 판정했다.

검토에서 두 가지를 짚었다.

- "준비 중"은 데이터에 없는 표현이다. 모델이 열거값 `READY`를 스스로 옮긴 말이고, 쇼핑몰 기준의 표현은 "출고 대기"다. 이 말은 주문 상태 `PREPARING`의 "상품 준비 중"과 비슷해서 고객이 두 상태를 구분하기 어렵다.
- 예상 배송일 2026년 1월 1일은 실험한 날인 2026년 10월 31일보다 앞선다. 데이터 생성기가 날짜를 고정해 두었고, 모델은 오늘 날짜를 모르므로 이상하다고 보지 않았다.

### 달랐던 이유

예측대로였다.

## 주문번호 없이 묻기

이 실험은 기록을 정리하기 전에 이미 해 보았다. 결과를 먼저 본 뒤라 예측은 남기지 않았고, 답의 문장도 남기지 않았다.

### 실제 결과

"제 주문 어디쯤 왔어요?"처럼 주문번호 없이 물으면 모델은 툴을 부르지 않고 주문을 찾지 못한다고 답했다. 인자를 지어내서 툴을 부르지는 않았다. 형식에 맞지 않는 주문번호를 주었을 때도 주문을 찾지 못했다.

## 마지막 확인

다음 Spring AI 코드의 `.call()` 뒤에서 일어나는 일을 말로 설명했다.

```kotlin
class OrderTools(private val orders: OrderService) {
    @Tool(description = "주문번호로 주문 상태를 조회한다")
    fun getOrder(@ToolParam(description = "주문번호") orderId: String): String =
        runBlocking { orders.getOrder(orderId).status.name }
}

val answer = chatClient.prompt()
    .user("주문번호 ORD-0001 지금 어디쯤 왔어요?")
    .tools(OrderTools(orderService))
    .call()
    .content()
```

### 답

1. 툴 정의는 `tools` 필드에 함수 선언 글로 바뀌어 실린다.
2. 툴 호출 응답은 `content`가 null이면서 툴 이름과 파라미터를 JSON 문자열로 준다.
3. 프레임워크가 내부의 루프에서 툴을 찾아서 실행하고, 인자는 직렬화로 바꾼다.
4. 실행 결과는 다음 요청의 메시지에 `content`로 들어간다.
5. 루프는 더 이상 툴 호출이 없을 때 끝난다.

### 검토

- 1번은 두 단계를 하나로 묶었다. HTTP 요청의 `tools` 필드에 실리는 것은 JSON 스키마다. Spring AI가 메서드 이름, `@Tool`의 설명, 파라미터 타입과 `@ToolParam`의 설명에서 이 스키마를 만든다. 함수 선언 글로 바꾸는 일은 요청을 받은 OpenAI 서버가 모델에 넣기 전에 한다. 첫 실험에서 토큰 수로 추정한 그 변환이다.
- 2번은 맞다. 빠진 것은 `finish_reason`이 `tool_calls`라는 점과, 툴 호출마다 결과의 짝을 맞출 `id`가 붙는다는 점이다.
- 3번에서 툴을 찾는 방식은 직접 만든 `ToolCatalog`와 같다. Spring AI는 툴을 이름으로 등록해 두고, 응답의 툴 이름으로 찾는다. 인자 문자열을 `orderId: String`으로 바꾸는 일은 직렬화가 아니라 역직렬화다. 반환값을 tool 결과 문자열로 바꾸는 일이 직렬화다. `@Tool` 메서드가 `suspend`가 아니어서 `runBlocking`으로 스레드를 막는다는 점도 이 코드에서 보인다.
- 4번에서 빠진 것이 있다. 결과는 `role`이 `tool`인 메시지의 `content`에 들어가고, 같은 메시지의 `tool_call_id`에 툴 호출의 `id`가 들어간다. 그 앞에는 모델이 보낸 assistant의 툴 호출 메시지가 그대로 다시 들어가야 한다.
- 5번은 맞다. 응답의 툴 호출 목록이 비면 그 응답의 `content`가 `.content()`의 값이 된다.

## 후반부로 넘길 문제

툴 호출 루프를 완성한 뒤 코드를 함께 읽으며 찾은 동작이다. 학습자가 고르지 않은 동작이고, 전반부에서는 고치지 않았다.

- 반복 횟수에 상한이 없다. 모델이 툴을 계속 부르면 루프가 멈추지 않고 요청마다 비용이 든다.
- 툴 실행 예외의 메시지가 `[툴 오류] <클래스 이름>: <메시지>` 그대로 모델에게 간다. 실제 서비스라면 내부 오류 메시지가 고객 답에 섞일 수 있다.
- 툴 결과의 열거값을 모델이 스스로 한국어로 옮긴다. `READY`를 "출고 대기"가 아닌 "준비 중"으로 옮긴 것이 그 예다.
- 모델은 오늘 날짜를 모르므로 이미 지난 예상 배송일을 그대로 전한다.
- 툴 결과가 클수록 다음 요청의 입력 토큰이 늘어난다. 상품 목록을 담은 `Order`는 `Shipment`보다 훨씬 크다.
- 응답의 `choices`가 빈 목록이면 `first()`가 예외를 던진다. 모델 호출 단계에서 넘긴 문제가 그대로 남아 있다.
- 자기 자신을 필드로 품는 입력 타입은 스키마를 만들 때 무한 재귀에 빠진다.

# 후반부

후반부에서는 전반부에서 넘긴 실패 후보를 일부러 일으키고, 실제로 드러난 실패만 고친다. 실험마다 실행하기 전의 예측, 실제 결과, 둘이 달랐던 이유를 적는다.

## 툴을 쓴 턴 다음에 툴 끄기

### 예측

"주문번호 ORD-0001 지금 어디쯤 왔어요?"로 툴을 쓴 뒤 `/tools off`를 하고 "고마워요."를 보낸다. 이 요청의 기록에는 툴 호출 메시지와 툴 결과 메시지가 있지만 `tools` 정의는 없다. 서버는 이 요청을 받아 줄 것이다. 툴 호출은 이미 끝난 대화이기 때문이다.

### 실제 결과

서버는 요청을 받아 주었다. "고마워요."에 대한 답은 "천만에요! 도움이 필요하시면 언제든지 말씀해 주세요."였고 입력 토큰은 184개, 출력 토큰은 21개였다.

입력 토큰 184개는 툴 정의가 빠진 크기와 맞는다. 직전 요청의 입력 207개에서 툴 정의 83개를 빼고, 직전 답의 출력 48개와 새 사용자 메시지를 더하면 이 크기가 된다. 툴을 끄면 툴 정의만 빠지고, 지난 툴 호출과 결과는 평범한 대화 기록으로 남는다.

툴을 대화 도중에 꺼도 실패하지 않으므로 고칠 것이 없다.

### 달랐던 이유

예측대로였다.

## 툴이 가끔 실패할 때

### 예측

`--faults flaky`로 서비스 호출이 20% 확률로 실패하게 하고, 툴 오류가 날 때까지 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 반복한다. 툴 오류를 받은 모델은 같은 툴을 다시 부르지 않고 고객에게 오류를 알릴 것이다. 그 답에는 내부 이름이 섞일 것이다.

### 실제 결과

툴 오류를 받은 모델은 고객에게 바로 알리지 않고 같은 툴을 한 번 더 불렀다. 두 경우를 보았다.

- 다시 부른 호출이 성공한 경우에는 정상 답을 냈다. 요청은 세 번 오갔고 입력 토큰은 150개, 193개, 289개였다. 고객에게 가는 답에는 오류가 있었다는 흔적이 없었다.
- 다시 부른 호출도 실패한 경우에는 "현재 배송 상태를 확인하는 데에 일시적인 문제가 발생하고 있습니다. 불편을 드려 죄송합니다."라고 답했다. 요청은 세 번 오갔고 입력 토큰은 150개, 193개, 271개였다.

두 경우 모두 답에 `SHIPPING.getShipment`나 `Unavailable` 같은 내부 이름은 섞이지 않았다.

검토에서 두 가지를 짚었다.

- 두 번째 실패의 답은 "주문 상태에 대해서는 계속 확인할 수 있으니, 조금만 기다려 주시겠어요?"로 끝났다. 에이전트에게는 기다렸다가 다시 확인하는 기능이 없으므로, 모델이 할 수 없는 일을 약속했다.
- 툴을 다시 부른 둘째 요청의 출력 토큰은 55개와 51개였다. 첫 툴 호출의 19개보다 크다. 원문 출력으로 확인하니 이 응답은 `tool_calls`와 함께 `content`에 "죄송합니다. 배송 상태를 조회하는 중에 문제가 발생했습니다. 다시 한 번 시도해 보겠습니다. 잠시만 기다려 주세요."를 담고 있었다. `finish_reason`은 `tool_calls`였다. 툴 호출 응답의 `content`가 늘 null인 것은 아니다. 지금 채팅은 툴 호출이 있는 응답의 `content`를 기록에만 넣고 화면에는 보여 주지 않는다.

### 달랐던 이유

모델은 한 번의 오류로는 고객에게 알리지 않고 다시 시도했다. 두 번 모두 오류일 때 오류라고 알려 주었다. 내부 이름은 모델이 고객용 문장으로 바꾸면서 걸러졌다.

### 고친 것

툴 호출 응답에 함께 온 문장이 화면에 보이지 않는 실패를 고쳤다. 고객이 재시도하는 동안 계속 기다릴 수 있으므로, 재시도하고 있다는 것을 중간에 알려 주는 편이 낫다고 보았다.

- `Agent.run(message, onProgress: (String) -> Unit = {})`로 알리는 통로를 `run`의 인자로 받는다. 턴마다 다른 출력처를 쓸 수 있다.
- 툴 호출 응답의 `content`가 비어 있지 않으면, 툴을 실행하기 전에 `onProgress`로 그 문장을 넘긴다.
- 알리는 내용은 중간 문장뿐이고, 채팅은 그 문장을 표시 없이 그대로 보여 준다. `[툴]` 줄은 지금처럼 턴이 끝난 뒤에 보인다.

## 오래된 데이터

이 실험은 하지 않고 쓰기 툴이 생기는 단계로 넘겼다. 오래된 읽기는 `ShopState`가 보관한 덮어쓰기 직전의 값을 돌려주는데, 데이터 생성기는 처음 상태를 바로 써 넣으므로 시작할 때 직전 값을 가진 주문이 없다. 상태를 덮어쓰는 교환 요청과 환불은 툴로 등록되어 있지 않아서, 모델 채팅에서는 `--faults stale`이 아무 효과도 내지 않는다. 이 실패는 에이전트가 상태를 바꾼 뒤 바로 다시 읽을 때 드러난다.

재시도 실험에서 함께 확인한 것도 있다. 일시적 오류가 나도 모델이 항상 재시도하는 것은 아니다. 재시도하라는 지시가 어디에도 없으므로, 모델은 대화를 읽고 그때그때 다시 부를지 정한다. 재시도 횟수를 보장하려면 모델이 아니라 코드가 재시도해야 한다.

## 큰 툴 결과

### 예측

"주문번호 ORD-0001 뭐 주문했는지 알려 주세요."를 보내 `get_order`를 부르게 한다. 둘째 요청의 입력 토큰은 `get_shipment` 때처럼 57개쯤 늘어날 것이다. `Order`에는 상품 이름이 없으므로 답에는 상품 코드만 나올 것이다.

### 실제 결과

모델은 `get_order`를 불렀고 요청은 두 번 오갔다. 툴 결과는 `{"id":"ORD-0001","customerId":"CUS-001","items":[{"sku":"SKU-009","quantity":3,"unitPrice":39000}],"status":"PREPARING","orderedAt":"2025-12-29T00:00:00Z"}`였다.

- 입력 토큰은 149개에서 233개로 84개 늘었다. 이 주문은 상품이 한 종류뿐이다.
- 답은 상품 코드 `SKU-009`, 수량 3개, 단가 39,000원, 주문 상태 "준비 중", 주문일 2025년 12월 29일을 나열했다. 상품 이름은 지어내지 않았다.

실패로 본 것은 두 가지다.

- 고객은 "SKU-009를 3개"로는 무엇을 샀는지 알 수 없다. 상품 이름은 `ShopState.products`에 있지만 툴 결과에 없었다.
- 주문 상태 `PREPARING`이 "준비 중"으로 나왔다. 배송 상태 `READY`도 앞 실험에서 "준비 중"이었으므로 고객에게는 두 상태가 같은 말이 된다.

### 달랐던 이유

`Order`에는 `Shipment`보다 필드가 많아서 입력 토큰이 더 늘었다. 필드 이름도 결과 JSON에 그대로 들어가 토큰이 된다.

### 고친 것

툴 결과로 도메인 객체를 그대로 내보내지 않고 툴용 결과 클래스를 따로 둔다.

- 상품 이름은 `get_product` 툴을 따로 만들지 않고 `get_order`의 결과에 담는다. 고객의 질문 하나에 툴 하나로 답하고 요청 횟수가 늘지 않는다.
- 상태의 뜻은 툴 설명에 적지 않고 결과에 표시용 필드로 담는다. 툴 설명에 적으면 툴을 부르지 않는 요청에도 입력 토큰이 붙고, 모델이 값과 설명을 맞춰 번역해야 한다.
- `get_order`는 `OrderView(id, items, status, statusLabel, orderedAt)`를 돌려준다. `items`의 원소는 `sku`, `name`, `quantity`, `unitPrice`를 가진다. 답에 쓰이지 않는 `customerId`는 뺐다.
- `get_shipment`는 `ShipmentView(orderId, status, statusLabel, eta)`를 돌려준다.
- 상태 문구는 정규식 응답기가 쓰는 `label()`을 그대로 써서, 두 응답기가 같은 말을 쓴다.

### 고친 뒤의 결과

같은 질문을 다시 보냈다. 답은 상품명 "노트북 거치대", 수량 3개, 단가 39,000원을 나열하고 주문 상태를 "상품 준비 중"이라고 전했다. 상품 코드는 답에서 사라졌다. 입력 토큰은 149개에서 242개로 93개 늘어, 고치기 전보다 9개 많다. 상품 이름과 상태 문구가 늘고 고객 ID가 줄어든 결과다.

## 반복 상한이 없는 루프

### 예측

"주문번호 ORD-0001 배송 상태를 확실해질 때까지 get_shipment로 반복해서 조회해 주세요."처럼 질문으로 툴을 반복해 부르게 부추긴다. 모델은 몇 번 부르다가 스스로 멈출 것이다.

### 실제 결과

모델은 `get_shipment`를 한 번만 부르고 멈췄다. 상태가 "출고 대기"로 확인되자 더 부르지 않았고, "배송 상태가 변경될 때까지 계속 확인해 주시겠습니까?"라고 되물어 판단을 고객에게 넘겼다. 요청은 두 번 오갔다.

이 실행은 `/reset` 없이 보내서 앞 실험의 주문 내역 대화가 기록에 남아 있었다. 첫 요청의 입력 토큰이 351개였던 것은 그 때문이다.

### 달랐던 이유

예측대로 스스로 멈췄지만 몇 번이 아니라 한 번이었다. 모델은 같은 툴을 같은 인자로 다시 부르면 같은 결과가 나올 것을 알기 때문에, 사용자가 반복을 부추겨도 툴 결과가 바뀌지 않으면 다시 부르지 않는다.

## 늘 실패하는 툴

### 예측

`--faults down`으로 모든 서비스 호출이 실패하게 하고 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 보낸다. 툴 결과는 매번 "일시적 오류"라고 말하지만 실제로는 성공하지 않는다. 모델은 `flaky` 실험처럼 두 번쯤 시도하다가 멈출 것이다.

### 실제 결과

모델은 `get_shipment`를 한 번 부르고 오류를 받자 다시 부르지 않았다. "죄송합니다. 현재 배송 상태를 확인하는 중에 오류가 발생했습니다. 잠시 후 다시 시도해 주시겠어요?"라고 답했고, 요청은 두 번 오갔다. 입력 토큰은 150개와 193개였다.

끝나지 않는 루프는 세 방법으로 시도해 모두 재현되지 않았다. 사용자가 반복을 부추기면 한 번, 툴이 가끔 실패하면 많아야 두 번, 툴이 늘 실패하면 한 번 부르고 멈췄다. 이 결과는 gpt-4o-mini와 지금의 시스템 프롬프트에 대한 관찰이다.

### 달랐던 이유

오류 상황에서 툴을 다시 부를지 말지는 확률적이다. 같은 "일시적 오류"라도 `flaky` 실험에서는 한 번 더 불렀고, 이번에는 부르지 않았다.

### 고친 것

끝나지 않는 루프는 재현되지 않았지만, 실제로 드러난 실패만 고친다는 원칙의 예외로 삼아 상한을 넣었다. 모델이 다시 부를 확률이 0이 아니면 긴 반복은 드물 뿐 언젠가 일어나고, 모델을 바꾸면 그 확률도 달라진다. 이 실패는 답 하나가 틀리는 데서 그치지 않고 비용과 시간을 끝없이 쓰므로, 상한은 실패가 났을 때 피해의 크기를 정하는 장치로 둔다.

- `AgentSettings.maxCallsPerTool: Int? = 3`은 한 턴 안에서 툴 하나를 실행할 수 있는 횟수다. null이면 상한을 두지 않는다.
- 횟수는 툴마다 따로 세고 턴마다 새로 센다. 한 툴이 문제여도 다른 툴은 계속 쓸 수 있다.
- 상한만큼 실행한 툴은 다음 요청의 툴 목록에서 뺀다. 모든 툴이 빠지면 툴 정의 없이 요청하므로 모델은 글로 답해야 한다.
- 목록에서 뺀 툴도 이름이 대화 기록에 남아 있어서 모델이 다시 부를 수 있다. 그래서 상한을 넘은 호출은 실행하지 않고 `[툴 오류] <툴 이름>는 이번 턴에 더 쓸 수 없습니다`를 툴 결과로 돌려보낸다. 툴 호출마다 짝이 되는 결과가 있어야 서버가 요청을 받아 준다.
- 한 응답에 같은 툴이 상한보다 많이 들어 있으면 앞의 호출만 실행하고 나머지는 같은 오류 결과로 채운다.

이 상한은 툴을 한 번도 부르지 않은 응답이 올 때까지 도는 루프 자체를 끝내 주지는 않는다. 모든 툴이 빠진 뒤에도 모델이 툴 호출을 보내면 오류 결과를 받고 다시 요청한다. 툴 정의가 없는 요청에서 모델이 툴을 부르는 일은 이번 실험에서 보지 못했다.

## 후반부 정리

후반부에서는 전반부에서 넘긴 실패 후보 다섯 가지를 일부러 일으켰다.

- 툴을 쓴 턴 다음에 툴을 꺼도 서버는 요청을 받아 주었다. 고칠 것이 없었다.
- 툴이 가끔 실패하면 모델이 툴 호출과 함께 쓴 문장이 화면에 보이지 않았다. 그 문장을 턴 도중에 바로 보여 주도록 고쳤다.
- 오래된 데이터는 상태를 바꾸는 툴이 없어서 재현할 수 없었다. 쓰기 툴이 생기는 단계로 넘겼다.
- 큰 툴 결과에서는 답에 상품 코드만 나오고 주문 상태와 배송 상태가 같은 말로 번역되었다. 툴용 결과 클래스에 상품 이름과 상태 문구를 담도록 고쳤다.
- 끝나지 않는 루프는 세 방법으로 시도해 재현되지 않았다. 그래도 확률적으로 일어날 수 있고 피해가 끝없이 커지므로 툴마다 실행 횟수에 상한을 두었다.

후반부에서 배운 것은 세 가지다.

- 모델의 행동은 같은 조건에서도 실행마다 다르다. 오류를 받고 다시 시도할지, 몇 번 시도할지가 그렇다. 일정해야 하는 동작은 모델이 아니라 코드가 맡아야 한다.
- 툴 결과는 도메인 객체를 그대로 내보내는 것보다, 고객에게 답하는 데 필요한 정보로 다시 짜는 편이 정확하다. 모델에게 번역이나 조합을 맡기면 그 빈자리를 그럴듯한 말로 채운다.
- 툴 목록은 모델에게 알려 준 것일 뿐이고, 무엇을 실행할지는 실행하는 쪽의 코드가 마지막으로 정해야 한다.

다음 단계로 넘기는 문제는 다음과 같다.

- 재시도를 코드가 맡을지 정하지 않았다. 지금은 모델이 그때그때 판단한다.
- 모델이 할 수 없는 일을 약속한다. "조금만 기다려 주시겠어요?"처럼 에이전트에게 없는 기능을 말했다.
- 오래된 데이터 실험은 쓰기 툴이 생긴 뒤에 한다.
- 한 턴의 요청 수에는 상한이 없다. 모든 툴이 빠진 뒤에도 모델이 툴을 부르면 요청이 계속 나갈 수 있다.
- 전반부에서 넘긴 문제 가운데 빈 `choices`, 재귀 입력 타입, 오늘 날짜를 모르는 문제는 그대로 남아 있다.
