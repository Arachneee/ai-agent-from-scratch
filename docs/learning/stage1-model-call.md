# 모델 호출 단계 학습 기록

이 기록은 모델 호출 단계 전반부의 실험을 남긴다. 실험마다 실행하기 전의 예측, 실제 결과, 둘이 달랐던 이유를 적는다.

## 첫 호출

### 예측

요청 본문은 다음과 같이 나간다.

```json
{"model":"gpt-4o-mini","messages":[{"role":"system","content":"너는 가상 쇼핑몰의 고객지원 상담원이다. 고객의 주문 조회, 배송, 교환, 환불 문의에 한국어로 친절하고 간결하게 답한다."},{"role":"user","content":"안녕하세요."}]}
```

`prompt_tokens`는 79로 예측한다. 시스템 프롬프트 70자와 사용자 메시지 6자를 글자 하나당 토큰 하나로 세고, 구분자와 시작, 끝 표시에 토큰 3개를 더했다.

### 실제 결과

`prompt_tokens`는 54였다. 예측보다 25개 적다.

응답의 나머지 값은 다음과 같았다.

- 답은 "안녕하세요! 무엇을 도와드릴까요?"였고 `completion_tokens`는 11, `finish_reason`은 `stop`이었다.
- 요청에는 `gpt-4o-mini`를 썼는데 응답의 `model`은 `gpt-4o-mini-2024-07-18`이었다.
- 추정 비용은 약 0.0206원이었다.
- 응답 헤더의 속도 제한 한도는 분당 요청 5,000개, 분당 토큰 2,000,000개였다.

### 달랐던 이유

토크나이저는 문자 단위로 자르지 않고 의미 있는 단위로 자르기 때문에 토큰 수가 훨씬 줄어든다.

## 출력 토큰 상한

### 예측

실행 전에 예측하지 않았다.

### 실제 결과

`max_tokens`를 5로 두고 보냈다.

- 답은 "먼저, 저희"에서 끊겼다. `completion_tokens`는 5였고 `finish_reason`은 `length`였다.
- `prompt_tokens`는 82였다. 첫 호출과 같은 채팅에서 이어서 보냈다.
- `system_fingerprint`가 첫 호출의 `fp_73c5e31c8b`에서 `fp_efe5482bd3`으로 바뀌었다.
- 추정 비용은 약 0.0214원이었다.

### 달랐던 이유

`prompt_tokens`가 82가 된 이유는 이전 메시지도 같이 보냈기 때문이다.

### 달랐던 이유

## 온도

### 예측

같은 질문을 세 번씩 보내면 온도 0에서는 세 답이 완전히 같고, 온도 1.5에서는 세 답이 서로 달라진다.

### 실제 결과

질문은 "배송 지연 사과 문구를 한 문장으로 써 줘"였고, 보낼 때마다 `/reset`으로 대화 기록을 비웠다. 입력 토큰은 여섯 번 모두 67이었다.

온도 0에서는 세 답이 글자 하나까지 같았고 출력 토큰도 모두 16이었다.

- 배송 지연으로 불편을 드려 진심으로 사과드립니다.

온도 1.5에서는 세 답이 모두 달랐고 출력 토큰도 13, 20, 23으로 달랐다.

- 배송이 지연되는 점 진심으로 사과드립니다.
- 배송 지연으로 인해 불편을 끼쳐드려 진심으로 사과드립니다.
- 배송 지연에 대해 사과드리며, 최대한 빠르게 상품을 안내해 드리겠습니다.

### 달랐던 이유

예측이 맞았다. 온도로 LLM 답의 다양성을 조절한다. 온도를 높이면 다음 토큰의 확률 분포가 펼쳐져서 확률적으로 다양한 답이 나올 수 있다. 또한 온도 0은 같은 답이 나올 가능성을 최대로 올린다.

## 여러 턴 대화의 입력 토큰

### 예측

`/reset` 뒤 온도 0으로 "안녕하세요.", "주문한 상품이 아직 안 왔어요.", "언제쯤 도착할까요?"를 이어서 보낸다. 다음 턴의 입력 토큰은 이전 턴의 입력 토큰, 이전 답의 출력 토큰, 새 질문의 토큰, 숨겨진 구분자 토큰 수를 더한 값이다.

### 실제 결과

세 턴의 토큰은 다음과 같았다. 질문의 토큰 수는 `o200k_base` 토크나이저로 셌다.

- 첫째 턴: 입력 54, 출력 11. 답은 "안녕하세요! 무엇을 도와드릴까요?"였다.
- 둘째 턴: 질문 토큰 11, 입력 84, 출력 37. 답은 주문 번호를 알려 주면 배송 상태를 확인하겠다는 내용이었다.
- 셋째 턴: 질문 토큰 10, 입력 139, 출력 25. 답은 다시 주문 번호를 요청하는 내용이었다.

예측한 식에 숨겨진 구분자 토큰 8개를 넣으면 두 턴 모두 실제 값과 정확히 맞는다.

- 둘째 턴: 54 + 11 + 11 + 8 = 84
- 셋째 턴: 84 + 37 + 10 + 8 = 139

### 달랐던 이유

예측이 맞았고, 숨겨진 구분자 토큰은 턴마다 8개였다. 첫 호출의 토큰 분해에서 44번부터 54번까지를 보면 숨은 토큰이 8개 있다. 직전 메시지의 끝 표시 1개, 새 user 메시지의 시작, 역할 이름, 경계, 끝 표시 4개, 답을 시작하는 assistant 표시 3개다. 새 턴이 붙을 때마다 이 8개가 그대로 다시 생긴다.

### 달랐던 이유

## 잘못된 API 키

### 예측

상태 코드는 401이다.

### 실제 결과

`OPENAI_API_KEY=sk-wrong`으로 보냈더니 상태 코드 401이 왔다.

- `code`는 `invalid_api_key`, `type`은 `invalid_request_error`였다.
- 메시지는 "Incorrect API key provided: sk-wrong. ..."였다. 보낸 키 값이 오류 메시지에 그대로 들어 있었다.
- 본문의 `Content-Type`은 `application/json`이 아니라 `text/plain`이었다.
- 본문에는 테스트 고정 데이터에 없던 `"status": 401` 필드가 더 있었다.

### 달랐던 이유

## 존재하지 않는 모델

### 예측

`/model gpt-4o-mini-typo`로 바꾸고 보내면 상태 코드는 404다. 처음에는 401로 예측했다가 실행 전에 404로 고쳤다.

### 실제 결과

잘못된 키를 그대로 둔 채 `/model gpt-4o-mini-typo`로 바꿔 보냈을 때는 404가 아니라 401이 왔다. 서버는 키를 먼저 확인하고, 인증에 실패한 요청은 모델 이름을 확인하는 단계까지 가지 않는다.

정상 키로 `/model akdfdsf`를 보냈더니 상태 코드 404가 왔다.

- `code`는 `model_not_found`, `type`은 `invalid_request_error`였다.
- 메시지는 "The model `akdfdsf` does not exist or you do not have access to it."였다.
- 본문의 `Content-Type`은 `application/json; charset=utf-8`이었다. 401 응답의 `text/plain`과 달랐다.
- 퇴역한 `gpt-4.1-nano`를 불렀을 때도 상태 코드 404와 `code` `model_not_found`가 똑같이 왔다. 둘을 구분할 수 있는 것은 메시지 문자열뿐이다.

### 달랐던 이유

## 속도 제한 응답

### 예측

`burst --count 100 --concurrency 50`으로 보내도 429는 나오지 않는다. 응답 헤더의 `x-ratelimit-limit-requests`가 5000이므로 5,000개까지는 받아 준다.

### 실제 결과

`burst --count 100 --concurrency 50`으로 보냈더니 100개 모두 200이었고 429는 나오지 않았다. 걸린 시간은 3,622ms였다. 마지막 응답의 속도 제한 헤더는 다음과 같았다.

```
x-ratelimit-limit-requests: 5000
x-ratelimit-limit-tokens: 2000000
x-ratelimit-remaining-requests: 4994
x-ratelimit-remaining-tokens: 1999996
x-ratelimit-reset-requests: 60ms
x-ratelimit-reset-tokens: 0s
```

이 설정으로는 429를 겪지 못했으므로, 429 재현은 후반부의 지연 프록시로 넘긴다.

### 달랐던 이유

429가 나오지 않는다는 예측은 맞았지만, 요청 100개를 쓴 뒤 남은 요청 수가 4,900이 아니라 4,994였다. 속도 제한이 토큰 버킷 알고리즘처럼 동작해서, 시간 간격마다 쓸 수 있는 양이 계속 채워지기 때문으로 보인다. 분당 5,000개는 12ms마다 하나씩 채워지는 속도이고, 3.6초 동안 약 300개가 채워져서 쓴 100개보다 많다. OpenAI가 정확한 알고리즘을 공개하지는 않았으므로 이 설명은 숫자에서 추론한 것이다.

### 달랐던 이유

## 주문 정보 없이 주문 상태 묻기

### 예측

`/reset` 뒤 온도를 끄고 "주문번호 ORD-0001 지금 어디쯤 왔어요?"를 보내면, 모델은 배송 상태를 지어내지 않고 모른다고 답한다.

### 실제 결과

모델은 배송 상태를 지어냈다. 한 번 보냈고, 답은 다음과 같았다.

> 안녕하세요! 주문번호 ORD-0001의 배송 상태를 확인해보겠습니다. 현재 주문은 배송 중이며, 예상 도착일은 내일입니다. 추가로 궁금한 점이 있으시면 언제든지 말씀해 주세요!

- 시드 42의 가짜 서비스에서 ORD-0001의 실제 상태는 "상품 준비 중"이고 배송은 "출고 대기"다. 모델의 답은 둘 다 틀렸다.
- 모델은 "확인해보겠습니다"라고 말했지만, 실제로 확인할 수단은 없었다.
- `finish_reason`은 `stop`이었고, 응답 어디에도 답이 지어낸 것이라는 표시는 없었다.
- 입력 67, 출력 50, 추정 비용 약 0.0561원이었다.

이어서 "주문번호 어디쯤 왔어요?"를 보냈는데, 모델이 알려 주지 않은 ORD-0001을 답에 넣었다. 이 질문이라면 입력 토큰이 62여야 하는데 실제로는 67이었다. 터미널에서 지운 글자가 실제로는 지워지지 않은 채 함께 전송된 것이었고, 다시 타이핑해 보내자 같은 일이 생기지 않았다. 모델이 아는 것은 모두 요청 본문 안에 있으므로, 이상한 답이 나오면 원문과 토큰 수부터 확인한다.

### 달랐던 이유

주문번호를 주니까 모델이 확인한 척하고 답을 지어냈다. 주문번호가 없을 때는 주문번호를 물었다.

### 달랐던 이유

## 비용

이번 주 실험의 호출 비용은 화면의 `[토큰]` 줄을 합산해 약 0.7원이었다. 요청 100개를 보낸 `burst`가 약 0.25원으로 가장 컸다. OpenAI 사용량 화면의 값도 비슷했다. 월 상한 5,000원의 0.02퍼센트 수준이다.

## 마지막 확인

처음 계획은 Spring AI 호출 코드를 보고 HTTP 요청과 응답을 손으로 적는 것이었다. JSON을 외우는 것은 의미가 크지 않다고 판단해서, 같은 코드에서 무엇이 어디로 가는지 말로 설명하는 방식으로 바꿨다. 대상 코드는 다음과 같다.

```kotlin
val answer = chatClient.prompt()
    .system("너는 쇼핑몰 상담원이다.")
    .user("배송은 보통 며칠 걸리나요?")
    .options(OpenAiChatOptions.builder().model("gpt-4o-mini").temperature(0.2).maxTokens(100).build())
    .call()
    .content()
```

### 답

- `.system(...)`과 `.user(...)`는 `messages` 리스트에 순서대로 들어간다. system과 user는 `role`에 해당하고, 안의 내용은 문자열 `content`가 된다.
- `.options(...)`의 값은 요청 본문에 추가되고, 주지 않으면 기본값이 들어간다.
- `.content()`는 응답 본문에서 모델이 실제로 만들어 낸 답을 꺼낸다. 그 과정에서 다른 정보는 버려질 수 있다.
- 같은 `chatClient`로 다음 질문을 하면 모델은 이전 질문을 기억하지 못한다. 기억하게 하려면 메모리가 필요하고, 메모리에서 꺼낸 이전 메시지를 `messages`에 이어 붙여야 한다.
- 키가 틀리면 401, 모델 이름이 틀리면 404가 돌아오고, 이 코드에서는 예외가 난다.

### 검토

다섯 가지 모두 흐름은 맞다. 다음 세 가지를 보탠다.

- 옵션의 세 값은 본문의 최상위 필드 `model`, `temperature`, `max_tokens`가 된다. 옵션을 주지 않았을 때 들어가는 기본값은 서버의 기본값이 아니라 Spring AI 설정의 기본값이다. `model`은 필수 필드라서 Spring AI가 설정값을 반드시 채워 보낸다.
- `.content()`는 `choices[0].message.content`를 꺼내고 `finish_reason`, `usage`, `id`, 실제 응답한 모델 스냅숏 이름을 버린다. `finish_reason`을 버리면 `max_tokens`에 걸려 잘린 답과 끝까지 쓴 답을 구분할 수 없고, `usage`를 버리면 호출 비용을 알 수 없다. 이 값이 필요하면 `.call().chatResponse()`로 응답 전체를 받는다.
- Spring AI는 401과 404 같은 4xx 응답을 재시도하지 않는 예외로, 429와 5xx 응답을 재시도할 수 있는 예외로 나눈다. 재시도할 수 있는 예외는 기본 설정으로 자동 재시도한다. 지금 만든 클라이언트에는 재시도가 없으므로, 이 차이가 후반부 재시도 설계의 출발점이다.

## 후반부로 넘길 문제

- 대화 기록을 쌓아 요청마다 다시 보내는 일은 지금 예제 모듈의 `ModelResponder`가 맡고 있다. 대화 기록에는 쇼핑몰 개념이 없고 다른 에이전트에도 필요하므로 프레임워크로 옮긴다. 툴 호출이 들어오면 `tool_calls`와 `tool` 역할 메시지 때문에 기록의 모양이 바뀌므로, 옮기는 일은 툴 호출 루프 단계에서 한다.
- 이 밖에 따로 꼽은 문제는 없다. 후반부는 로드맵의 모델 호출 단계에 적힌 재시도와 시간 제한, 응답 기록과 재생, 월 비용 상한, 로컬 모델 교체를 따른다.
