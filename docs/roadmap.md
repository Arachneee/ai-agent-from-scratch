# AI 에이전트 프레임워크 바닥부터 만들기 로드맵

## 목적

이 프로젝트는 AI 에이전트 개발을 깊이 이해하기 위한 공부 프로젝트다. 업무에 바로 붙일 결과물을 만드는 것보다 원리를 이해하는 것이 우선이다.

완료 시점의 목표 수준은 FDE(Forward Deployed Engineer)가 고객 현장에서 하는 일을 혼자 해낼 수 있는 수준이다. 모호한 요구를 받아 범위를 정하고, 실제 시스템에 붙는 에이전트를 만들고, 품질을 평가로 증명하고, 운영 가능한 상태로 배포할 수 있어야 한다.

학습 과제를 고를 때는 다음 다섯 방향을 기준으로 삼는다.

- 비즈니스에 영향을 주는 문제를 다룬다.
- 어떻게 만들지 바로 보이지 않는 문제를 파고든다.
- 성능 장애의 원인을 끝까지 추적한다.
- 복잡한 상태를 모델링한다.
- 실사용자가 핵심 비즈니스에 닿는 지점을 다룬다.

## 목표와 비목표

목표는 다음과 같다.

- 에이전트 프레임워크를 바닥부터 직접 구현하고, 프레임워크가 감추는 부분이 왜 그렇게 설계되는지 이해한다.
- 모든 개선을 실제로 겪은 문제에서 출발시키고, 개선 효과를 숫자로 확인한다.
- 마지막에 기성 프레임워크와 비교했을 때 각 설계의 장단점을 근거를 들어 설명할 수 있다.

비목표는 다음과 같다.

- 상용 수준의 범용 프레임워크를 만들어 공개하는 것은 목표가 아니다.
- 여러 모델 공급자를 지원하는 것은 목표가 아니다. OpenAI API와, OpenAI 호환 형식을 따르는 로컬 모델 서버만 다룬다.

다음 상황은 코드가 동작하더라도 실패로 본다.

- 문제를 겪어 보지 않은 채 일반적인 모범 사례를 미리 구현한다.
- 측정 없이 "나아진 것 같다"는 느낌으로 단계를 끝낸다.
- 프레임워크 모듈에 쇼핑몰 업무 개념이 새어 들어간다.

## 제약

- 언어는 Kotlin이다.
- 모델은 OpenAI API를 사용한다. Spring AI, LangChain4j, 공식 OpenAI SDK 같은 라이브러리를 쓰지 않고 HTTP로 직접 호출한다.
- 학습 시간은 일주일에 20시간 정도이고 기한은 없다. 끝까지 진행하는 것이 목표다.
- OpenAI API 비용은 한 달에 5,000원 이하로 유지한다. 이 상한은 로드맵 전체 설계에 영향을 준다. 자세한 운용 방식은 비용 상한 운용 절에 적는다.
- 고객 대화, 정책 문서, 평가 시나리오, 공격 시나리오는 모두 한국어로 작성한다.
- 예제의 고객, 주문, 결제 데이터는 모두 가짜로 만든다. 실제 회사 데이터나 실제 개인정보를 넣지 않는다.
- OpenAI API 키는 환경 변수로만 읽고 저장소에 커밋하지 않는다.
- 학습자는 Kotlin 백엔드 개발에 익숙하고, Spring AI로 툴 호출을 써 본 경험이 있다. 에이전트 루프를 직접 구현해 본 경험은 없다. 단계별 예상 기간은 이 출발점을 가정한다.
- 개발 장비는 Apple M3 Pro, 메모리 36GB다. 양자화한 14B에서 32B 크기의 오픈 모델을 로컬에서 돌릴 수 있으므로, 로컬 모델 실험은 이 장비에서 진행한다.

## 저장소 구조

저장소는 Gradle 다중 모듈로 나눈다.

**프레임워크 모듈**은 모델 호출, 툴 호출 루프, 컨텍스트 관리, 상태 관리, 메모리와 검색, 관측성, 평가 같은 에이전트 공통 기능을 담는다. 이 모듈은 특정 업무 영역을 알지 못해야 한다. 주문, 환불, 배송 같은 단어가 이 모듈의 코드에 나타나면 경계가 무너진 것으로 본다.

**예제 모듈**은 프레임워크를 가져다 쓰는 가상 쇼핑몰 고객지원 에이전트다. 가짜 외부 서비스와 실패 주입 스위치, 평가 시나리오도 이 모듈에 둔다.

## 예제 에이전트

예제는 가상 쇼핑몰의 고객지원 에이전트다. 고객이 채팅으로 주문 조회, 배송 지연 문의, 교환, 환불을 요청하면 에이전트가 처리한다.

에이전트는 가짜 외부 서비스 네 개와 통신한다.

- 주문 서비스는 주문 내역과 주문 상태를 관리한다.
- 결제 서비스는 결제와 환불을 처리한다.
- 재고 서비스는 교환 가능 여부를 확인한다.
- 배송 서비스는 배송 상태를 추적한다.

각 서비스에는 실패 주입 스위치를 둔다. 스위치로 응답 지연, 간헐적 오류, 속도 제한 응답, 일관되지 않은 데이터, 대화 도중의 상태 변경을 켜고 끌 수 있어야 한다. 상태 변경의 예로는 환불 요청을 처리하는 도중에 배송이 출발하는 상황이 있다.

이 예제를 고른 이유는 에이전트 핵심 기술이 모두 자연스럽게 필요해지기 때문이다. 툴이 많고, 주문 상태와 상담 상태가 엇갈리고, 환불 정책 문서를 검색해야 하고, 고액 환불처럼 되돌리기 어려운 행동이 있고, 고객 메시지가 신뢰할 수 없는 입력이다. 정답이 비교적 분명해서 평가를 세우기도 쉽고, 같은 영역의 공개 벤치마크인 tau-bench를 비교 기준으로 쓸 수 있다.

## 비용 상한 운용

한 달 5,000원은 작은 모델로도 수천 번 호출하면 넘는 금액이다. 그래서 OpenAI API는 실제 모델 동작을 확인해야 하는 곳에만 쓰고, 반복 실행은 로컬 모델과 기록된 응답으로 처리한다.

- 예제 에이전트의 기본 모델은 OpenAI의 가장 저렴한 소형 모델로 둔다. 큰 모델은 비교 실험에서만 짧게 쓴다.
- 평가 단계의 사용자 시뮬레이터와 LLM 채점, 반복 실행은 로컬 모델로 돌린다. 로컬 모델 결과가 OpenAI 모델 결과와 얼마나 다른지는 작은 표본으로 한 번 확인한다.
- 모델 호출 단계에서 응답 기록과 재생 기능을 먼저 만든다. 한 번 호출한 요청과 응답을 저장해 두고, 같은 요청이 오면 API를 부르지 않고 저장된 응답을 돌려준다. 프레임워크 코드를 고친 뒤 회귀를 확인할 때는 이 재생 모드를 기본으로 쓴다.
- 프레임워크에 월 비용 상한 장치를 둔다. 누적 비용이 상한에 가까워지면 경고하고, 상한을 넘으면 OpenAI 호출을 막고 로컬 모델로 전환하거나 실행을 멈춘다.
- 배포와 운영 단계의 부하 시험은 OpenAI 형식을 흉내 내는 가짜 모델 서버로 진행한다. 가짜 서버는 설정한 지연과 속도 제한 응답을 돌려준다.

## 단계 진행 방식

모든 단계는 같은 다섯 부분으로 진행한다.

- **문제**: 현재 에이전트가 무엇 때문에 실패하는지 한 문장으로 적는다.
- **재현**: 그 실패가 실제로 일어나는 입력이나 실패 주입 설정을 만들어 직접 겪는다.
- **측정**: 실패를 숫자로 확인한다. 개선 전 수치를 반드시 먼저 기록한다.
- **개선**: 원인을 추적하고 구조를 바꾼다. 이때 개선을 프레임워크에 넣을지 예제에 남길지 판단한다. 다른 에이전트에도 쓸모 있는 개선이면 프레임워크로 올리고, 쇼핑몰 업무에만 해당하면 예제에 남긴다.
- **확인**: 같은 재현 조건에서 지표가 나아졌는지 확인하고, 새로 드러난 한계를 기록한다. 이 한계가 다음 단계의 문제가 된다.

단계마다 학습 기록을 하나 남긴다. 학습 기록에는 다섯 부분의 내용, 개선 전후 수치, 프레임워크와 예제 사이의 배치 판단과 그 이유를 적는다.

아래 단계에 적힌 문제와 개선은 예상이다. 실제로 겪은 문제가 다르면 실제 문제를 따른다. 단계의 순서를 바꾸거나 단계를 쪼개도 된다.

## 실험 환경

**문제.** 실패를 일부러 일으키고 같은 조건에서 반복할 수 없으면, 개선이 효과가 있었는지 확인할 수 없다.

**만들 것.** Gradle 다중 모듈 골격을 만든다. 예제 모듈에 가짜 외부 서비스 네 개와 실패 주입 스위치를 만들고, 가짜 고객과 주문 데이터를 시드 값으로 재현 가능하게 생성한다. 터미널에서 대화할 수 있는 간단한 채팅 화면과, 정해진 시나리오를 한 번에 돌리고 결과를 숫자로 출력하는 최소한의 시나리오 실행기를 만든다.

**완료 기준.** 같은 시드와 같은 실패 주입 설정으로 실행하면 가짜 서비스가 같은 데이터와 같은 실패를 돌려준다.

**배우는 기술.** 재현 가능한 실험 설계, 실패 주입.

## 모델 호출

**문제.** 모델 호출이 네트워크 오류나 속도 제한 응답에 그대로 죽고, 상담 한 건에 토큰과 비용이 얼마나 드는지 모른다.

**재현.** 실제 API의 429 응답과 시간 초과를 겪어 보고, 응답 지연을 흉내 내는 로컬 프록시로 같은 상황을 반복한다.

**측정.** 호출 실패율, 호출당 입력 토큰과 출력 토큰, 호출당 비용.

**개선.** HTTP 클라이언트와 JSON 직렬화만으로 Chat Completions API를 호출한다. 지수 백오프 재시도, 시간 제한, 토큰 사용량 기록을 넣는다. 프레임워크에 모델 호출 인터페이스를 정의하고, OpenAI 호환 로컬 모델 서버로도 바꿔 끼울 수 있게 한다. 비용 상한 운용 절에 적은 응답 기록과 재생 기능, 월 비용 상한 장치도 이 단계에서 만든다.

**드러날 한계.** 모델이 주문 정보를 모르기 때문에 주문 상태를 지어내서 답한다.

**배우는 기술.** 채팅 메시지 형식, 토큰과 비용 계산, 재시도와 속도 제한 처리, 응답 기록과 재생.

## 툴 호출 루프

**문제.** 모델이 주문 정보를 조회할 수단이 없어 답을 지어낸다. 툴을 붙이면 이번에는 같은 툴을 끝없이 부르거나, 잘못된 인자로 부르거나, 툴 예외로 대화가 중단된다.

**재현.** 존재하지 않는 주문번호, 모호한 요청, 툴이 오류를 내는 실패 주입 설정으로 시나리오를 돌린다.

**측정.** 시나리오 성공률, 상담당 평균 루프 반복 수, 실패 유형별 건수.

**개선.** 툴 등록소를 만들고 Kotlin 함수 정의에서 JSON 스키마를 생성한다. 루프 종료 조건, 최대 반복 수, 같은 호출의 반복 감지를 넣는다. 툴 오류를 예외로 던지지 않고 모델이 읽을 수 있는 결과로 돌려준다. 여러 툴 호출을 코루틴으로 병렬 실행한다.

**드러날 한계.** 여러 단계를 거치는 상담에서 고객이 응답을 받기까지 수 초 동안 아무것도 보지 못한다.

**배우는 기술.** 함수 스키마 설계, 루프 제어, 툴 오류 처리, 병렬 툴 호출.

## 스트리밍

**문제.** 툴을 여러 번 부르는 상담에서 첫 응답이 나오기까지 오래 걸리고, 고객은 처리 중인지 멈췄는지 알 수 없다.

**재현.** 배송 서비스에 지연을 주입하고 툴 세 번 이상이 필요한 시나리오를 돌린다.

**측정.** 첫 토큰까지의 시간, 전체 응답 시간.

**개선.** 서버 전송 이벤트 형식의 스트리밍 응답을 직접 파싱한다. 스트림 중간에 조각나서 도착하는 툴 호출 인자를 조립한다. 툴 실행 중이라는 진행 이벤트를 채팅 화면에 보여준다.

**드러날 한계.** 상담이 길어지면 앞에서 말한 주문번호를 잊고, 턴마다 입력 토큰이 늘어 비용이 빠르게 커진다.

**배우는 기술.** 스트리밍 프로토콜 파싱, 스트림 중 툴 호출 처리, 응답 경험 설계.

## 컨텍스트 관리

**문제.** 긴 상담에서 초반에 나온 사실을 잊고, 전체 대화를 매번 보내기 때문에 턴이 늘수록 비용이 계속 커진다.

**재현.** 40턴 이상 이어지는 상담 시나리오를 만든다.

**측정.** 턴별 입력 토큰, 초반 사실을 후반에 올바르게 사용한 비율, 상담당 비용.

**개선.** 토큰 수를 계산하고 오래된 대화를 잘라내거나 요약한다. 주문번호처럼 잃으면 안 되는 사실을 따로 고정한다. 프롬프트 앞부분을 바뀌지 않게 유지해 OpenAI의 자동 프롬프트 캐싱이 적용되는지 확인한다.

**드러날 한계.** 대화 도중 주문 상태가 바뀌면 에이전트가 이미 환불한 주문을 다시 환불하거나, 교환 진행 중에 환불을 시작한다. 프롬프트 지시만으로는 절차를 강제할 수 없다.

**배우는 기술.** 토큰 예산 관리, 요약 전략, 프롬프트 구조와 캐싱.

## 상태 모델링

**문제.** 상담 절차가 프롬프트에만 적혀 있어서, 주문 상태가 대화 도중 바뀌면 에이전트가 정책을 위반하는 행동을 한다.

**재현.** 환불 처리 중 배송 출발, 교환 접수 후 재고 소진 같은 상태 변경을 실패 주입으로 일으킨다.

**측정.** 시나리오당 정책 위반 행동 수, 잘못된 상태 전이 수.

**개선.** 상담을 상태 기계로 모델링하는 추상화를 프레임워크에 만든다. 상태마다 허용되는 툴을 제한하고, 상태 전이 조건을 코드로 검사한다. 모델이 판단할 부분과 코드가 강제할 부분의 경계를 정한다. 실행 상태를 직렬화할 수 있게 해서 체크포인트를 남긴다.

**드러날 한계.** 창고 확인처럼 오래 걸리는 응답을 기다리는 동안 프로세스가 재시작되면 진행 중이던 상담이 사라진다.

**배우는 기술.** 상태 기계와 그래프 기반 실행, 모델 판단과 코드 강제의 경계 설계, 체크포인트.

## 내구성 실행

**문제.** 오래 걸리는 작업 도중 프로세스가 죽으면 상담이 유실되고, 재시도하면 환불이 두 번 실행된다.

**재현.** 창고 확인 응답을 몇 분 뒤에 돌려주도록 설정하고, 대기 중에 프로세스를 강제 종료한다. 환불 툴 실행 직후 응답이 오기 전에 종료하는 경우도 만든다.

**측정.** 재시작 후 상담 복구율, 중복으로 실행된 부작용 수.

**개선.** 실행 단계를 저장소에 기록하고 재시작 시 마지막 체크포인트에서 재개한다. 부작용이 있는 툴에 멱등성 키를 붙인다. 외부 응답 대기와 시간 초과를 상태로 표현한다.

**드러날 한계.** 환불 규정과 교환 규정을 묻는 질문에 에이전트가 그럴듯하지만 틀린 규정을 답한다.

**배우는 기술.** 이벤트 기록 기반 재개, 멱등성, 장기 실행 작업 설계.

## 검색 증강과 메모리

**문제.** 수십 쪽짜리 정책 문서를 프롬프트에 모두 넣을 수 없고, 넣지 않으면 규정을 지어낸다. 다시 찾아온 고객의 이전 상담 내용도 기억하지 못한다.

**재현.** 가짜 정책 문서 묶음과, 정답이 문서의 특정 조항에 있는 질문 목록을 만든다. 일부 질문은 비슷한 조항 여러 개 중 하나만 맞도록 만든다.

**측정.** 정책 질문 정답률, 검색 재현율(정답 조항이 상위 k개 안에 들어온 비율), 질문당 토큰.

**개선.** 문서를 청크로 나누고 OpenAI 임베딩 API로 벡터를 만든다. 벡터 저장소를 먼저 전수 비교 방식으로 직접 구현하고, 문서가 늘어 느려지면 근사 최근접 탐색을 도입한다. 키워드 검색을 섞은 하이브리드 검색과 재순위화를 실험한다. 한국어는 조사와 어미가 붙어 단어 단위로 자르면 키워드 검색이 잘 맞지 않는다. 먼저 글자 두 개씩 묶는 방식으로 직접 구현하고, Lucene의 Nori 형태소 분석기와 검색 재현율을 비교한다. 검색을 툴로 노출해 모델이 필요할 때 부르게 한다. 고객별 장기 메모리를 저장하고 다음 상담에서 불러온다.

**드러날 한계.** 개선했다고 믿지만, 프롬프트 한 줄을 바꾸면 다른 시나리오가 깨지는지 알 방법이 없다.

**배우는 기술.** 청크 분할 전략, 임베딩과 벡터 검색, 하이브리드 검색, 한국어 토큰화, 검색 품질 측정, 장기 메모리.

## 평가

**문제.** 변경이 품질을 올렸는지 떨어뜨렸는지 감으로 판단하고 있고, 모델 응답이 매번 달라서 한 번 돌려 본 결과를 믿을 수 없다.

**재현.** 프롬프트를 조금 바꾸고 시나리오 전체를 여러 번 돌려 결과가 흔들리는 것을 확인한다.

**측정.** 시나리오별 성공률, 같은 시나리오를 k번 돌려 모두 성공한 비율(tau-bench의 pass^k).

**개선.** 0단계의 시나리오 실행기를 평가 체계로 키운다. 고객 역할을 맡는 사용자 시뮬레이터 에이전트를 만든다. 대화가 끝난 뒤 가짜 서비스의 최종 상태를 기대 상태와 비교해 채점한다. 최종 상태로 판단할 수 없는 응답 품질은 LLM 채점으로 평가하고, 사람 채점과 비교해 LLM 채점의 신뢰도를 검증한다. 평가를 회귀 테스트로 돌릴 수 있게 한다. 비용 상한 때문에 시뮬레이터와 채점, 반복 실행은 로컬 모델로 돌리고, 같은 실행을 다시 볼 때는 기록된 응답을 재생한다.

**드러날 한계.** 어떤 시나리오가 실패했는지는 보이지만, 수십 번의 모델 호출 중 어디서 왜 틀렸는지는 알 수 없다.

**배우는 기술.** 평가 데이터셋 설계, 사용자 시뮬레이션, 상태 기반 채점, LLM 채점과 그 검증, 비결정성 다루기.

## 관측성과 원인 추적

**문제.** 평가 실패 건이 어느 단계에서 틀렸는지 모르고, 상담 응답 시간의 상위 5퍼센트 구간이 느린데 어느 호출이 느린지 모른다.

**재현.** 배송 서비스에 간헐적 지연과 오류를 주입하고, 평가에서 실패한 시나리오를 고른다.

**측정.** 단계별 지연 시간 분포, 단계별 토큰과 비용, 실패 원인을 찾는 데 걸린 시간.

**개선.** 에이전트 실행을 추적 구간으로 기록한다. 모델 호출, 툴 호출, 상태 전이를 각각 구간으로 남기고 OpenTelemetry의 생성형 AI 의미 규약을 참고한다. 모델 호출 단계에서 만든 응답 기록을 추적 구간과 연결해서, 실패한 실행 하나를 그대로 재생해 결정적으로 재현하는 기능으로 키운다. 상담별 비용과 지연을 집계한다.

**드러날 한계.** 고객 메시지에 숨긴 지시로 에이전트가 정책을 어기고 전액 환불을 하거나 다른 고객의 주문을 조회한다.

**배우는 기술.** 분산 추적 설계, 실행 재생, 지연과 비용 분석, 장애 원인 추적.

## 보안과 가드레일

**문제.** 프롬프트 주입으로 정책 위반 환불, 다른 고객 정보 조회, 개인정보 노출이 일어난다.

**재현.** 공격 시나리오 묶음을 만든다. 직접 주입, 주문 메모나 배송 메시지처럼 툴 결과에 숨긴 간접 주입, 역할극을 이용한 우회를 포함한다.

**측정.** 공격 성공률, 정상 요청을 잘못 거부한 비율.

**개선.** 툴 권한을 모델 판단이 아니라 세션의 고객 신원에 묶는다. 입력과 출력을 검사하는 가드레일 단계를 넣는다. 일정 금액 이상 환불은 상담원 승인을 받도록 실행을 멈추고, 승인 뒤 재개한다. 이 흐름은 상태 모델링과 내구성 실행 단계의 구조를 재사용한다. 응답에서 개인정보를 마스킹한다.

**드러날 한계.** 가드레일과 추가 검사 때문에 상담당 비용과 지연이 목표를 넘는다.

**배우는 기술.** 프롬프트 주입 방어, 권한 설계, 사람 승인 흐름, 과잉 차단과 미차단 사이의 균형.

## 비용과 지연 최적화

**문제.** 상담 한 건의 비용과 응답 시간 상위 5퍼센트 구간이 목표치를 넘는다.

**재현.** 평가 시나리오 전체를 돌려 상담당 비용과 지연 분포를 측정한다. 이 단계를 시작할 때 목표치를 먼저 정한다.

**측정.** 상담당 비용, 응답 시간 분포, 평가 성공률. 성공률이 떨어지지 않는 것이 조건이다.

**개선.** 요청을 분류해 단순 문의는 작은 모델로, 복잡한 분쟁은 큰 모델로 보낸다. 구조화 출력으로 형식 오류에 따른 재시도를 줄인다. 응답 캐싱, 독립적인 호출의 병렬화, 프롬프트 접두부 안정화를 적용한다. OpenAI 호환 로컬 모델로 일부 단계를 대체하는 실험을 한다.

**드러날 한계.** 툴과 규칙이 계속 늘어 단일 에이전트의 프롬프트가 비대해지고, 툴 선택 정확도가 떨어진다.

**배우는 기술.** 모델 라우팅, 구조화 출력, 캐싱, 지연 예산 설계, 품질과 비용의 교환 관계 측정.

## 다중 에이전트

**문제.** 툴이 수십 개로 늘면서 에이전트가 엉뚱한 툴을 고르는 일이 잦아진다.

**재현.** 툴 수를 단계적으로 늘리며 같은 시나리오를 돌린다.

**측정.** 툴 수에 따른 툴 선택 정확도, 평가 성공률, 상담당 비용.

**개선.** 분류 에이전트와 환불, 배송, 교환 전문 에이전트로 나눈다. 대화를 넘기는 방식과, 다른 에이전트를 툴처럼 부르는 방식을 둘 다 구현하고 비교한다. 단일 에이전트 구성과 성공률, 비용, 지연을 비교해서, 다중 에이전트가 손해인 경우도 수치로 확인한다.

**드러날 한계.** 새 외부 시스템을 붙일 때마다 프레임워크와 예제에 연동 코드를 손으로 작성해야 한다.

**배우는 기술.** 에이전트 분할 기준, 위임과 핸드오프, 다중 에이전트의 조정 비용.

## 프로토콜 연동

**문제.** 외부 시스템마다 툴 연동 코드를 따로 짜야 하고, 이미 MCP 서버로 제공되는 도구를 쓸 수 없다.

**재현.** 공개된 MCP 서버 하나를 예제 에이전트에 붙여 보려고 시도한다.

**측정.** 새 시스템 하나를 연동하는 데 바뀌는 코드 줄 수와 걸린 시간.

**개선.** JSON-RPC 위에서 동작하는 MCP 클라이언트를 프레임워크에 직접 구현한다. 가짜 쇼핑몰 서비스를 MCP 서버로 노출하고, 에이전트가 툴 목록을 동적으로 받아 쓰게 한다. 표준 입출력 방식과 HTTP 방식을 모두 다룬다.

**드러날 한계.** 에이전트가 터미널에서만 동작해서 다른 사람이 써 볼 수 없다.

**배우는 기술.** MCP 프로토콜 구조, JSON-RPC, 동적 툴 발견.

## 배포와 운영

**문제.** 에이전트가 로컬 터미널에서만 동작하고, 여러 고객이 동시에 쓸 때 어떤 일이 생기는지 모른다.

**재현.** 가짜 모델 서버에 속도 제한과 지연을 설정하고, 동시 상담 수를 늘리는 부하를 만들어 속도 제한과 자원 경합을 겪는다.

**측정.** 동시 상담 수에 따른 오류율과 지연, 운영 중 평가 점수.

**개선.** 에이전트를 HTTP 서버로 띄우고 스트리밍을 지원하는 웹 채팅 화면을 붙인다. 컨테이너로 배포한다. 공유 속도 제한을 관리하는 요청 대기열을 넣는다. 실제 대화를 표본 추출해 자동 채점하는 운영 중 평가와 사용자 피드백 수집을 만든다. 지인 몇 명에게 고객 역할로 써 보게 하고 그 대화를 평가 데이터셋에 추가한다.

**드러날 한계.** 직접 만든 프레임워크가 기성 프레임워크와 비교해 어디가 낫고 어디가 부족한지 모른다.

**배우는 기술.** 에이전트 서비스 배포, 동시성과 속도 제한, 운영 중 평가, 피드백 순환.

## 기성 프레임워크 비교

**문제.** 실무에서는 기성 프레임워크를 고르는 일이 많은데, 무엇을 기준으로 골라야 하는지 판단할 근거가 없다.

**진행.** 예제의 한 부분을 JVM 프레임워크인 Spring AI, LangChain4j, Koog로 다시 구현한다. Python과 TypeScript 기반인 OpenAI Agents SDK와 LangGraph는 소스 코드를 읽고 직접 만든 설계와 대응시킨다. 같은 평가 시나리오로 성공률, 비용, 코드 양을 비교한다.

**완료 기준.** 각 프레임워크가 툴 루프, 상태, 내구성, 관측성을 어떻게 다루는지 정리한 비교 문서가 있고, 어떤 상황에서 무엇을 고를지 근거를 들어 설명할 수 있다.

**배우는 기술.** 프레임워크 설계 해독, 선택 기준 수립.

## 종합 과제

**문제.** 모든 단계를 쇼핑몰 예제 하나로만 진행했기 때문에, 프레임워크가 정말 업무 영역과 무관한지, 처음 보는 요구를 혼자 납품까지 끌고 갈 수 있는지 검증되지 않았다.

**진행.** 쇼핑몰과 다른 영역의 가상 고객 요구서를 하나 받는다. 요구서는 일부러 모호하게 만든다. 요구서를 다른 AI에게 쓰게 하거나 지인에게 부탁해서, 본인이 내용을 미리 정하지 않도록 한다. 다음 순서로 진행한다.

- 요구서를 읽고 범위와 성공 기준을 정의하는 문서를 쓴다.
- 성공 기준을 평가 시나리오로 먼저 만든다.
- 직접 만든 프레임워크로 에이전트를 구현한다.
- 평가로 품질을 증명하고 배포한다.
- 비용, 품질, 남은 위험을 담은 운영 보고서를 쓴다.

**완료 기준.** 프레임워크 모듈을 고치지 않거나 최소한만 고치고 새 에이전트를 납품한다. 프레임워크를 고쳐야 했다면 그 이유를 기록한다.

**배우는 기술.** 문제 정의, 범위 협상, 평가 우선 개발, 납품과 보고.

## 기술 선택

다음은 로드맵 작성 시점의 기본값이며, 단계를 진행하며 바꿔도 된다.

- 빌드는 Gradle Kotlin DSL, 런타임은 JDK 21을 쓴다.
- HTTP 호출은 Ktor 클라이언트, JSON 직렬화는 kotlinx.serialization을 쓴다. 코루틴과 자연스럽게 맞물리기 때문이다.
- 모델 API는 Chat Completions 형식을 기준으로 한다. OpenAI 호환 로컬 모델 서버들이 같은 형식을 지원해서 모델 라우팅과 로컬 모델 실험에 그대로 쓸 수 있기 때문이다. Responses API는 모델 호출 단계에서 비교 실험으로 다룬다.
- 모델은 큰 모델 하나와 작은 모델 하나를 설정값으로 둔다. 구체적인 모델 이름은 진행 시점의 최신 모델로 정한다.
- tau-bench에서는 pass^k 지표와, 대화 뒤 최종 상태를 비교하는 채점 방식만 빌려 온다. 데이터 구조와 툴 목록, 과제는 tau-bench에 맞추지 않고 직접 설계한다. 점수를 tau-bench와 직접 견주는 것은 목표가 아니다.
- 배포와 운영 단계의 배포 대상은 그 단계에서 정한다. 기본값은 로컬 컨테이너이고, 지인이 써 보는 기간에만 접근 인증을 붙여 외부에 잠시 공개한다.

## 구현자에게 맡기는 부분

- 모듈과 패키지 이름, 프레임워크의 공개 API 형태.
- 테스트 라이브러리, 저장소 종류, 웹 채팅 화면의 기술.
- 가짜 서비스를 같은 프로세스 안에 둘지 별도 HTTP 서버로 둘지의 결정. 프로토콜 연동 단계 전까지는 어느 쪽이든 된다.
- 단계별 학습 기록의 위치와 형식.
